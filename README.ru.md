# K-Line на macOS: пассивный захват, анализ и обход ограничения CH340/CH341

Исходный проект содержал пустой notebook.ipynb и окружение .venv; существующего Python-кода serial/K-Line/OBD не было.

## Главный результат: как заставить CH340/CH341 будить K-Line блок

**Проблема.** Дешёвые USB-UART адаптеры на CH340/CH341 не работают с диагностическими
программами (OpenDiag и аналоги) на K-Line, тогда как PL2303 и FTDI работают. При этом
K-Line обвязка (транзисторный каскад или драйвер вроде L9637D) у них одинаковая. Причина
долго оставалась неясной.

**Что измерено в этом проекте** (все тесты — на реальном железе, macOS, pyserial):

1. **Передача данных.** Loopback-тест (TX замкнут на RX) показал: CH340 передаёт и
   принимает байты **без потерь и искажений** на всех скоростях, включая нестандартную
   10400 бод. То есть проблема **не** в скорости и **не** в потере байтов.
   См. `tools/loopback_test.py`.

2. **BREAK.** K-Line fast-init (ISO 14230 / KWP2000) начинается с «wake-up pattern» —
   низкого уровня на линии длительностью ~25 мс. Обычно его формируют UART-командой BREAK.
   Тест показал: **CH340 не формирует BREAK вообще** — при `break_condition=True` на
   приёме (loopback) не появляется ни одного байта `0x00` ни при какой длительности.
   Для сравнения, **PL2303 BREAK формирует** — отсюда и разница «PL2303 работает,
   CH340 нет». См. `tools/break_test.py`.

3. **Обход.** CH340 **умеет** сделать тот же длинный низкий уровень **без BREAK** —
   отправкой байта `0x00` на низкой скорости. При 360 бод, 8N1, один байт `0x00` =
   1 старт-бит + 8 нулевых бит данных = 9 бит низкого уровня = **25.0 мс**. Loopback
   подтвердил, что чип реально держит линию низкой всё это время. См. `tools/lowbaud_test.py`.

4. **Проверка на блоке.** С этим методом (360 бод `0x00` → пауза → 10400 бод → init-кадр)
   CH340 **разбудил реальный блок** (климат Lada Kalina, адрес B1) и прочитал живые данные:
   ответ `61 01 ...` на запрос `21 01`. Метод встроен в `elm327_wifi.py`
   (`LiveTransport._init_once`).

**Вывод.** Дело не в K-Line обвязке и не в скорости, а в том, что CH340/CH341 не умеет
формировать BREAK (низкий уровень нестандартной длительности). Это обходится программно,
без пайки: BREAK заменяется на `0x00` @ 360 бод.

### Ограничения метода (важно)

- Длительность импульса измерена на хосте (loopback), **не** осциллографом на самой K-Line.
  Ответ блока косвенно подтверждает импульс, но точную форму сигнала на проводе здесь не меряли.
- Импульс ~25 мс получается только на 360 бод. После низкого уровня идёт высокий стоп-бит,
  поэтому фаза «высокого» по ISO 14230 укорочена; на блоках с жёсткими допусками может не сработать.
- Смена скорости порта не атомарна: между импульсом и кадром есть случайные задержки ОС/USB,
  поэтому нужны повторы (несколько попыток init).
- Реализован только **fast init**. Медленный **5-baud init** (ISO 9141) не поддержан.
- Проверено на **одном** блоке и **одном** экземпляре CH340 на одной версии macOS-драйвера.
  На другом железе/ОС поведение может отличаться.
- Полярность вашей K-Line обвязки может инвертировать сигнал — проверяйте на своём адаптере.

### Диагностические утилиты

Для проверки своего адаптера (замкните TX↔RX для loopback/break/lowbaud тестов):

```sh
python3 tools/loopback_test.py /dev/cu.usbserial-XXX   # теряет ли чип байты на 10400
python3 tools/break_test.py    /dev/cu.usbserial-XXX   # умеет ли чип BREAK (CH340 — нет)
python3 tools/lowbaud_test.py  /dev/cu.usbserial-XXX   # формирует ли 0x00@360 длинный низкий уровень
python3 tools/rts_dtr_test.py  /dev/cu.usbserial-XXX   # отрабатывают ли линии RTS/DTR (альтернативный обход)
```

Имя порта узнавайте командой `python3 -m serial.tools.list_ports`
(CH340 определяется как `USB2.0-Ser!`, VID:PID `1A86:7523`).

## Экспериментальный ELM327 Wi-Fi мост

`elm327_wifi.py` поднимает TCP-сервер, к которому можно подключиться диагностической
программой как к Wi-Fi ELM327. Мост прозрачно пробрасывает KWP-запросы на блок через
USB-K-Line адаптер, выполняя описанный выше wakeup автоматически. Подробности и
ограничения — в `docs/ELM327_WIFI.md`.

```sh
python3 -m serial.tools.list_ports
python3 elm327_wifi.py --mode live --host 0.0.0.0 --tcp-port 35000 \
  --port /dev/cu.usbserial-XXX --baudrate 10400
```

Порядок с блоком: запустить мост → подключиться программой → **включить зажигание**
(блок просыпается в этот момент, init поймает окно). Разовый опрос без TCP:
`python3 elm327_wifi.py --mode live --probe --port /dev/cu.usbserial-XXX --init-attempts 60`.

Не открывайте TCP-порт в интернет: аутентификации и шифрования нет.

## Захват

```sh
python3 kline_sniffer.py \
  --port /dev/cu.usbserial-XXX \
  --baudrate 10400 \
  --frame-gap-ms 20 \
  --output captures/kline.jsonl
```

Все эти значения — значения по умолчанию. Файлы не перезаписываются: для следующего захвата выберите новое имя. Каталог создаётся автоматически. Если порт не открылся, могут остаться пустые файлы захвата; используйте другое имя или удалите их вручную.

Дополнительные режимы:

```sh
python3 kline_sniffer.py --output captures/session2.jsonl --raw --verbose
python3 kline_analyze.py captures/kline.jsonl --top 10 --header-bytes 4
```

`--raw` сохраняет каждый полученный байт также в `captures/session2.jsonl.bin` без разделителей и метаданных. `--verbose` выводит каждый байт и интервал относительно предыдущего в stderr; это интервалы получения приложением, а не точные интервалы на проводе. Интенсивный вывод может влиять на тайминги.

Пример отображения (иллюстрация, не результат измерения):

```text
port=/dev/cu.usbserial-XXX baudrate=10400 format=8N1 frame_gap_ms=20 output=captures/kline.jsonl raw=off verbose=False
Passive read; timing is measured at host receipt. Ctrl+C to stop.
1791555792.123456  len=   5  81 11 F1 81 04  |.....|  [gap]
```

Строка JSONL:

```json
{"ts": 1791555792.123456, "ts_end": 1791555792.127456, "data": "81 11 F1 81 04", "length": 5, "reason": "gap"}
```

`ts` — Unix timestamp первого байта, `ts_end` — последнего, по часам компьютера. Для определения пауз используются монотонные часы. `reason` равен `gap`, `interrupted` или `error`; последние два обозначают потенциально незавершённый кадр. Анализатор учитывает все записи, показывает причины завершения и читает также минимальный формат с ts/data/length. Без ts_end интервал от конца кадра неизвестен. Некорректная запись завершает анализ с номером строки. Большие файлы требуют памяти: анализатор загружает весь захват.

Чтение бинарное, по одному байту, без decode. ASCII справа содержит только печатные символы 0x20–0x7E; остальные заменены точками. Кадр завершается при наблюдаемой паузе строго больше порога. При Ctrl+C и ошибке чтения накопленный кадр записывается перед закрытием файлов. JSONL сбрасывается после каждого кадра, raw — после каждого байта (это не гарантия сохранности при потере питания). При ошибке записи на диск полное сохранение невозможно.

## Ограничения оборудования и времени

Скрипт использует 8N1, отключает software/hardware flow control и устанавливает RTS/DTR в False до открытия. Он не вызывает serial.write, break и инициализацию K-Line. Однако ОС/драйвер могут кратковременно переключать RTS/DTR при открытии; электрическую пассивность гарантирует схема адаптера, а не Python. Используйте пригодный для прослушивания K-Line интерфейс; обычный UART нельзя подключать непосредственно к автомобильной K-Line. Для полностью пассивного прослушивания нужен подходящий приёмный тракт без воздействия TX на шину.

10400 — нестандартная скорость: macOS/pyserial поддерживают нестандартные значения, но конкретный адаптер или драйвер может отказать. Подробности: [pySerial API](https://pyserial.readthedocs.io/en/latest/pyserial_api.html).

USB и драйвер буферизуют данные. Даже read(1) не восстанавливает исходные паузы между байтами; USB-пакет может объединить несколько кадров, задержка приложения — создать ложное разделение. Порог 20 ms — эвристика, а не спецификация протокола. Для точных физических таймингов нужен аппаратный захват с временными метками. Один приёмный канал сам по себе не определяет направление обмена.

Отсутствие порта, отказ доступа, занятый порт, неподдерживаемая скорость и отключение USB выводятся в stderr с ненулевым кодом завершения. Если данных нет, программа продолжает ждать; молчание само по себе не означает отключение. Ctrl+C — штатное завершение. Закройте другие программы, использующие порт; проверьте подключение и права. Не запускайте от root без выяснения причины ошибки.

## Следующие шаги для определения протокола

1. Записать несколько сессий с известными действиями диагностического прибора, включая начало соединения, оставаясь пассивным наблюдателем. Без активного собеседника на шине может быть тишина.
2. Проверить скорость и формат физическим измерением; сопоставить результаты при разных порогах кадров и убедиться, что границы устойчивы.
3. Сравнить повторяющиеся префиксы, длины, пары запрос–ответ и последние байты. Проверять гипотезы полей длины и контрольных сумм на многих разных кадрах, а не на одном примере.
4. Сопоставить запись инициализации, адресацию, структуру сообщений и тайминги с документацией ISO 9141-2 и ISO 14230/KWP2000 и документацией конкретного ECU. По скорости 10400 и общему префиксу однозначно определить протокол нельзя. Инициализация с другой скоростью/импульсами может не сохраниться корректно в захвате UART при фиксированных 10400; здесь полезен логический анализатор с подходящим K-Line трактом.
5. Если стандартные структуры не согласуются с несколькими сессиями, исследовать вариант производителя или проприетарный протокол. Анализатор намеренно не присваивает полям смысл и не определяет протокол автоматически.

## Проверка без оборудования

```sh
python3 -m py_compile kline_sniffer.py kline_analyze.py
python3 -m unittest discover -s tests -v
```

Тесты используют модель последовательного порта, не открывают оборудование и не требуют pyserial. Реальные тайминги USB, поддержка 10400 и электрическая пассивность требуют отдельной аппаратной проверки.
